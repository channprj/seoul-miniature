# 그림을 만드는 절차

경복궁과 여의도 두 지도의 그림은 같은 틀로 만들었습니다.

1. 공개 지도 데이터로 **Blender 3D 장면**을 세웁니다. 배치·높이·실루엣은 여기서 정해집니다.
2. 고정 카메라 하나로 **조건 렌더**를 뽑습니다(색·물체 ID·깊이).
3. 색 렌더를 겹치는 창으로 잘라 이미지 편집 모델에 넣어 **양식만** 픽셀아트로 바꿉니다.
4. 모델이 바꾸면 안 되는 곳을 조건 렌더 기준으로 되돌리고(**굽기의 잠금**), 128색으로 줄여 타일로 자릅니다.
5. 같은 렌더의 깊이·ID 로 뷰어용 깊이 맵·분류 맵을 만듭니다.

이 문서는 단계마다 무엇을 넣고 무엇이 나오는지, 숫자는 얼마였는지, 왜 그렇게 했는지를 적습니다. 쓴 스크립트는 [`pipeline3d/`](../pipeline3d/README.md)에, 프롬프트 원문은 [PROMPTS.md](PROMPTS.md)에, 안 됐던 것은 [LESSONS.md](LESSONS.md)에 있습니다. 2026-11-10 까지 쓰던 2D 밑그림 방식은 [PIPELINE-2D-legacy.md](PIPELINE-2D-legacy.md)에 남겨 두었습니다.

## 1. 입력 자료

| 자료 | 쓴 곳 | 라이선스 |
|---|---|---|
| OpenStreetMap: 건물 윤곽·`building:part`·높이 태그, 도로·철도·교량, 수면, 녹지·공원, 담(`barrier=wall`), 나무 점 | 두 지도의 배치 전부 | ODbL 1.0 |
| 국토교통부 GIS건물통합정보(V-World 건물 정보)의 높이·층수 | 경복궁 일대 건물 높이 | 공공누리 제1유형 |
| Overture Maps 건물 테마, East Asian Buildings | 경복궁 일대 풋프린트 보충 | ODbL / CC BY 4.0 |
| 국가유산청 「경복궁 3D 기록」: 광화문·월대 일원, 전각 46건 | 경복궁 전각의 형태 | 공공누리 제1유형 |

- 여의도 건물 높이는 OSM 의 `height` → `building:levels` 순으로 읽고, 둘 다 없으면 건물 종류와 바닥 면적으로 추정했습니다(`pipeline3d/yeouido/prep.py` 의 `est_height`). 국토부 자료는 여의도에 쓰지 않았습니다.
- 국가유산청 파일은 다운로드 페이지에서 로그인과 이용 신청서를 거쳐 받습니다. 원본 FBX·텍스처와 변환한 3D 파일은 이 저장소에도 배포물에도 없습니다. 모델은 장면에 배치해 렌더하는 데만 썼습니다.
- FBX 에는 지도 좌표계가 없습니다. 건물마다 OSM 윤곽에 맞춰 돌리고 옮겼습니다. 현존하지 않는 건물의 모델은 배치하지 않았습니다.

**눈으로만 참고한 것.** 사진(위키미디어 공용의 자유 라이선스 사진), 지도 서비스의 거리뷰, 위성·항공 사진은 사람이(작업한 에이전트가) 보고 형태·색·옥상 배치를 3D 모델에 옮기는 데만 썼습니다. 이미지 모델의 입력으로 넣지 않았고, 저장소나 그림에 들어가지 않았습니다. 확인용으로 받은 사진은 보고 지웠습니다. 이전 판에서 모델에 참조 이미지로 넣었던 사진의 목록은 `pipeline/refs.json` 에 남아 있습니다(지금 그림에는 쓰이지 않습니다).

AI 학습용으로만 쓰라는 조건이 붙은 항공영상은 입력으로 쓰지 않았습니다. 판단 기준은 [LICENSING.md](LICENSING.md)에 있습니다.

## 2. Blender 장면

Python 에서 `bpy`(Blender 5.0.1 휠)를 불러 장면을 코드로 만듭니다. Blender 앱을 열어 손으로 고치지 않습니다. 한 번 실행이 화면의 한 창(타일)을 만들고 렌더까지 합니다.

- 경복궁: `pipeline3d/gyeongbokgung/gen.py <x0> <y0> <출력 이름>`
- 여의도: `pipeline3d/yeouido/gen_area.py <판> <x0> <y0> <출력 이름>`. 랜드마크는 `lm_build.py` 에 따로 있습니다.

### 일반 건물(절차 규칙)

이름난 건물이 아닌 곳은 윤곽과 높이에서 규칙으로 세웁니다. 세부는 나중에 이미지 모델이 채우므로, 장면에는 **모델이 따라 그릴 뼈대**만 있으면 됩니다. 처음에는 평평한 상자였는데, 그러면 모델이 상자를 그대로 두거나 배치를 무시했습니다. 조건 그림의 세부가 모자랐던 것이 원인이었습니다(LoRA 없이 40스텝을 돌려도 같았습니다).

- 벽: 층·칸(3.2 m) 단위 텍스처를 PIL 로 직접 그립니다. 창틀·유리·벽돌 줄·1층 상가와 차양(60%)·실외기가 들어갑니다. 텍스처는 사진이 아니라 색 표에서 만듭니다.
- 평지붕: 파라펫(난간 턱), 옥탑(25%), 물탱크(55%, 노랑·파랑·흰색), 실외기(0–2개), 평상(30%). 확률은 건물 OSM ID 로 고정한 난수라 다시 렌더해도 같습니다.
- 한옥: 풋프린트의 거리장으로 지붕 높이를 만들고(우진각·맞배·팔작·중층, 처마 들림), 기와골 요철과 마루를 넣습니다.
- 궁궐: 기단·월대(큰 전각은 2단), 붉은 기둥·단청 띠 벽, 큰 처마, 문루. 담은 OSM `barrier=wall` 선을 따라 사괴석 담 + 기와 지붕으로 세웁니다.
- 나무: 수관 덩어리 + 줄기. 경복궁은 1,337그루에 숲 자리 164그루를 더했고, 여의도는 OSM 나무 점과 공원 면에서 놓습니다.
- 여의도에 더한 것: 아파트(흰 벽 + 반복 창, 승강기 옥탑), 타워(띠창 텍스처, 높이 100 m 이상이면 옥상 헬리패드, 60 m 이상이면 냉각탑·물탱크·기계실), 교량(상판·교각·난간, 이웃 상판 위로는 난간을 세우지 않음), 호안·둔치·선착장, 철도·역.

**옥상 소품은 건물 종류마다 다르게.** 처음에는 모든 평지붕에 같은 소품 문장을 썼더니 타워 옥상에 파라솔과 장독이 올라갔습니다. 장면 쪽에서 타워에는 헬리패드·기계실을, 아파트에는 승강기 옥탑·물탱크만 두고, 프롬프트도 창 안 건물의 종류(저층·타워·아파트)에 맞는 문장만 넣게 바꿨습니다([PROMPTS.md](PROMPTS.md)의 B_LOW·B_TOWER·B_APT).

**밀도.** 모델에게 맡기는 소품 양은 세 단계로 시험했습니다. 절제판(소품 거의 없음), 빼곡판(「월리를 찾아라」처럼), 중간판(옥상당 2–4개, 지면은 조용히). 빼곡판은 "차 없음"이라고 적어도 차를 그렸고, 한옥 지붕에 천창을 냈고, 평평한 지면에 아스팔트 도로를 지어냈습니다. 중간판(m1)에서는 셋 다 0이었고 이것을 기본으로 삼았습니다.

### 랜드마크(사진 대조)

이름난 건물은 전용 모델을 만듭니다. 순서는 이렇습니다.

1. 자유 라이선스 사진을 **넓은 면·좁은 면·옥상**이 다 보이게 여러 장 찾습니다(63빌딩은 샛강 쪽, 강 위, 한강공원, 아파트 옥상, 역 쪽 등 9장).
2. 모델을 만들기 전에 실루엣·곡선 방향·홈·띠·꼭대기 처리·색을 글로 적습니다.
3. OSM `building:part` 와 높이를 뼈대로 쓰고, 사진과 다른 곳을 고칩니다.
4. 옥상은 위성·항공 사진을 보고 헬리패드·기계실·팬 위치를 맞춥니다.
5. 고친 뒤 렌더 창 몇 곳에서 전·후를 견주고, ID 패스가 그대로인지(윤곽을 건드리지 않았는지) 확인합니다.

**63빌딩 사례.** 처음 모델은 OSM 파트(120 m 높이까지 8.4 m 날개)만 보고 "위로 갈수록 좁아지는 볼록한 곡선"으로 만들었습니다. 그런데 바로잡아야 할 것은 모서리 곡면이 아니라 입면의 세로 윤곽이었습니다. 사진을 여러 각도로 보니 다음과 같았습니다.

- 넓은 두 면(북서·남동)이 아래로 갈수록 바깥으로 휘어 퍼지고, 좁은 끝면은 평면입니다. 그래서 끝면 윤곽이 A 자입니다. 퍼짐은 아래 60% 쯤에서 끝납니다.
- 끝면 가운데에 전망 승강기 통로가 **튀어나와** 꼭대기까지 오릅니다. 처음 모델은 이것을 오목한 홈으로 만들었습니다.
- 끝면에 짙은 가로 띠가 두 곳(높이의 약 32%, 60%), 모든 면의 꼭대기 아래(약 93%)에 하나 있습니다.
- 유리는 채도 높은 노랑이 아니라 고운 격자의 장밋빛 금색이고, 칸마다 밝기 차가 거의 없습니다(칸마다 밝기를 다르게 하면 벽돌처럼 보입니다).
- 안테나는 지붕 가운데가 아니라 강 쪽 끝에서 1/4 지점에 있습니다.

파크원(면 양 끝의 붉은 기둥 쌍, 팔각 꼭대기), 더현대 서울(긴 변의 붉은 잎 모양 트러스), IFC(깎인 결정 형태), 국회의사당(열주, 돔), LG트윈타워, FKI타워(평지붕, 층마다 가로 줄무늬)도 같은 방식으로 고쳤습니다. 사진으로 확인하지 못한 부분(거래소 외장, FKI 컨퍼런스센터 지붕 형태)은 추정이라고 코드 주석에 남겼습니다.

### 툰 재질(랜드마크)

굽기 단계에서 랜드마크 벽은 조건 렌더를 그대로 쓰게 됐습니다(아래 5절). 그러자 매끈한 3D 렌더 결이 이웃의 픽셀아트 타워 사이에서 튀었습니다. 그래서 랜드마크 재질만 픽셀아트 결에 가깝게 바꿨습니다(`lm_build.py` 의 `toon_mat`, `grid_tex`, `mat_frame`).

- **3단 명암**: 카메라 광선에만 `Emission = 바탕색 × (1.28 | 0.90 | 0.62) × 0.6 + Principled × 0.4`. 세 단 중 어느 것을 쓸지는 해 방향과 면 법선의 내적으로 고릅니다. 그림자·반사 광선은 원래 재질이라 이웃 화소는 바뀌지 않습니다. 지붕(법선 z > 0.9)은 원래 재질 그대로입니다.
- **창 격자 선**: 칸마다 밝기 잡음 없이, 창 칸 경계에 유리색 × 0.45 의 어두운 선(폭 약 0.27 m ≈ 12.5 cm 그림의 2 px)을 긋습니다. 1 px 선은 굽기의 포스터라이즈에서 점선으로 끊겨서 굵혔습니다. 텍스처 보간은 Closest.
- **붉은 부재 윤곽**: 파크원 기둥·크라운·가로보와 더현대 마스트의 면 가장자리 0.17 m 를 0.35 배로 어둡게 해서, 평평한 붉은색 + 1–2 px 짙은 테가 되게 했습니다.
- 국회 돔에도 같은 3단 명암을 줘서 부드러운 음영이 계단 음영이 됐습니다.

재질만 바꾸고 윤곽·높이·ID 는 그대로 두었습니다. 렌더 창 10곳에서 ID 패스가 한 화소도 달라지지 않은 것을 확인했습니다. 그래서 양식 패스를 다시 돌리지 않고 조건 렌더와 굽기만 다시 했습니다.

## 3. 카메라와 조건 렌더

- **정사투영**, 수평에서 **35°** 내려다봅니다. 엄밀한 아이소메트릭이 아니고, 회전도 없습니다. 경복궁은 북서쪽을 보고, 여의도는 남쪽을 봅니다(격자 도로가 화면 가로·세로와 나란하지 않게 하려고 방위를 고른 것입니다).
- 화면 좌표: 월드(로컬 m, z 위)의 점 P 에 대해 `px = (P·ex − cx)/m + W/2`, `py = H/2 − (P·ey − cy)/m`, 깊이 = `(P − cam_location)·view_dir`. 카메라 값은 `assets/*/map.json`(여의도)과 `assets/web-poc/scene.json`(경복궁)에 있습니다. 투영 코드는 `src/geom.js` 입니다.
- 렌더 엔진은 Cycles(CPU)입니다. 한 타일은 2752 × 1696 px 이고 8 × 8 = 64 타일을 이어 붙입니다. `_z.png` 가 이미 있는 타일은 건너뛰므로 중간에 끊겨도 이어 갈 수 있습니다.

한 타일에서 나오는 파일:

| 파일 | 내용 |
|---|---|
| `t_i_j.png` → `cond.png` | 색 조건 그림(RGB). 양식 패스의 입력 |
| `t_i_j_id.png` → `cond_id.png` | 물체 ID = R·256 + G(Cycles pass_index). 지면 1, 국가유산청 모델 2, 건물 10000+, 담 21000+, 나무 22000+(경복궁) |
| `t_i_j_z.png` → `cond_z.png` | 깊이 16비트를 R·256 + G 로. 경복궁 `2040 + v × 0.025` m, 여의도 `1141 + v × 0.05` m |
| `t_i_j_meta.json` → `meta.json` | ID → 종류(`lowrise`, `apartment`, `tower`, `landmark:63`, `bridge:마포대교`, `wall`, `tree` …) |

이어 붙인 뒤 점검(`stitch_halfF.py`): 자홍(텍스처 누락) 화소, ID 0, meta 에 없는 ID, 빈 타일, 타일 경계 단차(경계 열 차이 ÷ 바로 안쪽 열 차이). 여의도 렌더는 넷 다 0건, 경계 단차 비 1.57 이었습니다. 텍스처 누락은 병렬 렌더가 같은 임시 텍스처 파일을 덮어쓴 경합 때문이었고, 프로세스마다 임시 폴더를 따로 두어 고쳤습니다.

그다음 0.5 m 분류 맵(`classes_05m.png`)과 랜드마크 맵(`landmarks_05m.png`)을 만듭니다. 창마다 프롬프트에 넣을 문장을 고를 때 씁니다.

## 4. 양식 패스

### 모델과 설정

| 항목 | 값 |
|---|---|
| 모델 | Qwen-Image-Edit-2511 fp8(`qwen_image_edit_2511_fp8mixed.safetensors`), 텍스트 인코더 `qwen_2.5_vl_7b_fp8_scaled`, VAE `qwen_image_vae` |
| LoRA | Qwen-Image-Edit-2511-Lightning 8-step(bf16), 강도 1.0 |
| 샘플링 | 8스텝, Euler, flow matching(ModelSamplingAuraFlow shift 3.1, simple 스케줄), CFGNorm 1.0 |
| CFG | 1.0, 부정 프롬프트 없음(긍정 조건을 양쪽에 같이 넣는다) |
| 디노이즈 | 1.0. 조건 그림은 참조 이미지(reference latent)로만 들어가고 시작 잡음은 순수 잡음 |
| 창 | 1408 × 1024 px, 겹침 128 px. 22016 × 13568 캔버스에서 18 × 15 = 270창 |
| 시드 | 213(공개판 둘 다) |

디노이즈 0.8·0.6(조건 렌더를 시작 그림으로)은 3D 렌더 느낌이 남아 버렸습니다. 이전 그림을 양식 참조(두 번째 이미지)로 넣으면 픽셀이 굵고 거칠어졌습니다. 그래서 조건 그림 하나 + 디노이즈 1.0 으로 정했습니다. 시드 11 과 213 을 견주면 213 쪽이 광화문 석축·월대를 더 잘 지켰고, 시드 편차가 방식 차이보다 컸습니다.

ComfyUI 그래프 모양(워커가 보내는 것, `common/hd_worker.py` 의 `graph`):

```
UNETLoader(qwen_image_edit_2511_fp8mixed) ─ LoraLoaderModelOnly(Lightning 8-step, 1.0)
  ─ ModelSamplingAuraFlow(shift 3.1) ─ CFGNorm(1.0) ─┐
CLIPLoader(qwen_2.5_vl_7b_fp8_scaled, qwen_image) ───┼─ IsoHDTasks(작업 파일 목록)
VAELoader(qwen_image_vae) ───────────────────────────┘
```

`IsoHDTasks`(`common/iso_hd_tasks.py`)는 작업 파일 하나를 받아 셋 중 하나를 합니다.

- `enc`: 창 그림을 VAE 로 인코드하고 `TextEncodeQwenImageEditPlus` 로 프롬프트 + 그림을 조건으로 만들고, reference latent 를 붙여 저장합니다.
- `den`: 조건 + 잠재값 조각 + sigma → 그 창의 x0 예측. 모델을 한 번 부릅니다.
- `dec`: 잠재값 조각 → PNG.

### 이음매: 공유 latent

창을 따로따로 그리면 이웃 창이 겹침 띠를 다르게 그립니다. 그대로 자르면 벽·옥상·도로가 선을 따라 끊기고, 섞으면 반투명한 유령 소품이 생깁니다. 그래서 캔버스 전체 크기의 **잠재값 하나**를 두고 스텝마다 이렇게 합니다(`common/hd_coord.py`).

1. 270창 각각의 조각을 잘라 `den` 작업으로 큐에 넣습니다.
2. 워커들이 창별 x0 예측을 돌려줍니다.
3. 겹침 띠에서는 가장자리로 갈수록 작아지는 가중치(128 px 램프)로 예측을 평균해 캔버스 하나의 x0 를 만듭니다.
4. Euler 한 스텝을 캔버스 전체에 적용합니다.

8스텝이 끝나면 창 단위로 디코드해 픽셀에서 같은 램프로 이어 붙입니다.

2 × 2 블록 시험에서 블렌드 전 겹침 띠의 차이(|A − B| 평균, 0–255)는 공유 2.23, 독립 31.21 이었습니다. 띠 안에 결함이 한 건(옥탑 상자가 반투명으로 그려짐) 있었습니다. 겹친 두 창이 그 자리를 서로 다르게 예측한 평균이라 전 지도에서 띠를 검수해야 합니다.

### 창마다 다른 프롬프트

창마다 분류 맵을 보고 실제로 있는 것에 대한 문장만 끼웁니다. 없는 것을 말하면 모델이 그것을 지어냅니다. 랜드마크 문장은 그 건물이 창에 충분히 들어올 때만 넣습니다(건물 화소의 35% 이상, 또는 창 면적의 35% 이상). 조립 규칙과 원문은 [PROMPTS.md](PROMPTS.md)에 있습니다.

### 작업 큐와 GPU

- 조정자 1개와 GPU 마다 워커 드라이버 1개가 같은 공유 폴더(`run_dir`)를 봅니다. 작업은 파일입니다. 워커는 `todo/` 에서 `claimed/<이름>/` 으로 rename 해서 가져가고(원자적), 처리 중에는 파일의 수정 시각을 갱신합니다. 오래 갱신되지 않은 작업은 조정자가 `todo/` 로 되돌립니다. 그래서 GPU 를 중간에 빼거나 더할 수 있습니다.
- 공개판 실행에는 GPU 3장을 썼습니다: RTX A6000(48 GB), RTX 3090(24 GB), 통합 메모리 약 120 GB 의 ARM 장비 한 대. 경복궁 공개판에서 스텝 작업을 나눠 가진 비율은 대략 49 : 31 : 20 이었습니다.
- 걸린 시간(조정자 로그): 경복궁 1차 64분, 공개판 67분, 여의도 공개판 59분. 디코드는 그 안에서 약 50초입니다. 한 장으로 돌리면 270창에 약 2.9 시간으로 추정했습니다(창·스텝당 약 4.5 s).
- 남이 같이 쓰는 장비라서 카드에 다른 프로세스가 뜨면 그 카드의 워커를 빼는 도구를 따로 썼습니다(공개하지 않았습니다. 장비 이름이 박혀 있습니다).

한 장비에서 돌리는 예는 `pipeline3d/common/run_style_pass.sh` 입니다.

## 5. 굽기(bake)

양식 결과(`raw.png`)를 그대로 쓰지 않는 이유는 모델이 **지어내기** 때문입니다. 마당에 정자를 세우고, 강물 위에 섬과 상가를 그리고, 다리 위에 집을 얹고, 담에 진열창을 냅니다. 굽기는 조건 렌더(`cond`)를 정답지로 삼아 그런 곳을 찾아 되돌리고, 뷰어 자산을 만듭니다.

```bash
python build_assets.py    all --raw RAW --pass PASS --work WORK --jobs 16   # 경복궁
python build_assets_yd.py all --raw RAW --pass PASS --work WORK --jobs 16   # 여의도
```

단계는 `cache → lock → quant → maps → tiles → keys`(여의도는 tiles 뒤에 `mapjson`)입니다. 단계 이름을 주면 그 단계만 다시 돌고, `lock --crop x0,y0,x1,y1` 로 한 구역만 시험할 수 있습니다. CPU 만 쓰고 프로세스 16개 이하로 막아 두었습니다.

| 단계 | 하는 일 | 시간(경복궁 예행 / 여의도) |
|---|---|---|
| cache | 22016 × 13568 PNG 들을 한 번 풀어 npy(mmap)로 | 71 s / 21 s |
| lock | 아래 잠금들 | 289 s / 약 460 s |
| quant | 128색 median-cut(디더 없음) + 피라미드 | 94–170 s / 약 170 s |
| maps | `depth_rg8.png`, `classes.png`, `crown.png` | 47–105 s / 35–38 s |
| tiles | 256 px 타일 + `manifest.json`, `bg.png`, `bg_1x.png` | 5–8 s / 8–9 s |
| mapjson | 여의도 `map.json`(카메라·깊이 상수·앵커·경로) | – / 1 s |
| keys | 셰이더 색 키 통과율 비교(아래) | 11–91 s / 3 s |

### 잠금의 공통 원리

- **기대색**: cond 색 → raw 색의 대응표를 만듭니다. cond 를 5·4·3비트 칸으로 나누고, 같은 칸 raw 색의 다듬은 평균을 씁니다. 양식 패스는 색을 일정하게 옮기므로(밝은 회색 → 조금 따뜻한 회색), 대응표를 거친 기대색과 raw 를 견줘야 "다르게 그린 곳"만 남습니다.
- **덩어리**: 크로마 거리(작은 창 평균)가 문턱을 넘는 곳 → 열기(가는 선은 빠짐) → 성분 → 크기 조건 → 조금 키움. 열기 크기가 중요합니다. 차선·횡단보도·난간처럼 가는 것은 모델이 그린 픽셀아트로 남기고, 속이 찬 덩어리(지어낸 집·섬)만 잡기 위해서입니다.
- **보호**: 건물·담·나무 등 다른 물체 ID 의 둘레 몇 px 는 건드리지 않습니다(처마 선·윤곽선 보존).
- **채움**: 기대색 + 가까운 깨끗한 칸의 잔무늬(raw − 기대색). 결을 붙이지 않으면 민무늬 판이 됩니다.

### 양자화와 타일

- 128색 median-cut, 디더 없음. 이전 판의 96색 고정 팔레트는 오차가 평균 14.18 / p95 30.15 라 버렸습니다(새 팔레트 6.58 / 15.56, 경복궁).
- 최상위 단계(경복궁 6.25 cm, 여의도 12.5 cm)를 양자화한 뒤 BOX 축소하고 같은 팔레트로 다시 양자화해 아래 단계를 만듭니다. 리샘플 뒤에 다시 양자화하지 않으면 경계에 새 색이 생깁니다.
- `make_tiles.py`: z1(통짜 2752 × 1696) + z2·z4·z8 256 px 타일. 한 색으로만 찬 타일은 파일 없이 manifest 에 색만 적습니다. 쓴 타일을 다시 읽어 원본과 바이트 단위로 같은지 확인합니다.

### keys: 셰이더 색 키 확인

뷰어 셰이더는 팔레트 색표가 아니라 색 임계값(초록인가, 파란가, 유리색인가, 기와색인가)으로 효과 대상을 고릅니다. 새 그림에서 클래스별로 그 키를 통과하는 비율을 세어 이전 그림과 견줍니다. 예(경복궁 예행 세트): 궁 지붕의 기와색 통과율 0.86(이전 0.69), 물의 파랑 0.92(0.90). 여의도에서는 민트색 옥상 때문에 지붕 화소의 초록 비율이 0.139 → 0.306 으로 올라 잔디 판정에 걸리는지 따로 봤습니다.

## 6. 뷰어로 넘기는 것

| 파일 | 만드는 단계 | 내용 |
|---|---|---|
| `tiles/manifest.json`, `tiles/z1.png`, `tiles/z{2,4,8}_x_y.png` | tiles | 확대 단계별 그림 |
| `bg.png`, `bg_1x.png` | tiles | 통짜 그림(z2, z1). 타일을 못 쓸 때 |
| `depth_rg8.png` | maps | 2752 × 1696, 칸 안 최솟값 깊이, v = R·256 + G, B = 0, 65535 = 없음. 경복궁 `2060 + v × 0.02`(0.5 m 칸, 지면은 평면으로 폄), 여의도 `1141 + v × 0.05`(1 m 칸, 수면 −1.8 m·호안 경사를 그대로 둠) |
| `classes.png` | maps | 0–11. 0 없음 1 지면 2 도로 3 녹지 4 물 5 궁궐 마당 6 지붕 7 벽 8 궁궐 지붕 9 궁궐 벽 10 나무 11 보행로. 벽은 화면 위로 갈 때 높이 변화가 수직 벽의 0.55–2.2배인 화소 |

| `map.json`(여의도) | mapjson | 캔버스, m/px, 깊이 상수, 카메라, 랜드마크 앵커(지도 px), 차로·철도·배·보행 경로. 공개판에서는 굽기 입력 경로 키(`raw`)를 뺀다 |
| `winfaces.json`(여의도) | 설치 뒤 따로 | 밤 창문 면 격자: 벽면마다 층·칸 주기와 위상(그림의 창틀에서 잼). 앱이 첫 확대 때 계산하던 것을 미리 해 둔 것 |

경복궁의 차선·보행 경로는 `assets/web-poc/scene.json` 에 있습니다(이전 판에서 만든 것을 그대로 씁니다). 형식은 [APP.md](APP.md)에 있습니다.

그림을 다시 구우면 깊이·분류 맵이 바뀝니다. 그때 `winfaces.json` 도 다시 만들어야 합니다. 앱은 면 칸의 0.5% 넘게 벽이 아니면 파일을 버리고 실행 중 계산으로 돌아갑니다.
